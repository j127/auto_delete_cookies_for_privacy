# Firefox manual test matrix

The gate for every Firefox (AMO) release, first written as the merge gate for the Firefox port (issue #290): run every row once per browser channel on a real, headed Firefox before the release, record the outcome in the Result columns, and file a follow-up issue for every failure (reference it in the row). Automated coverage notes say what the unit/regression suites already pin so the manual pass can focus on what only a real browser shows.

Automated companion: `just e2e_firefox` drives a real headless Firefox through rows 1–12 and 14–19 (and the row-13 plumbing), plus the Support page's system details and bug-report email (#435, #436), with a privileged extension-page probe and chrome-context script — run it before starting a manual pass; the rows it covers then only need spot-checking, and each row's Automated coverage cell names what stays manual (the popup and right-click keeps of rows 7, 8 and 11, the Allow click of row 15, the restart parts of rows 6 and 10, and a mail app actually opening for the email link). It uses the default Firefox install; `FIREFOX_BIN=/path/to/firefox` points it at another channel, such as the ESR, so run it once per channel. CI's `e2e-firefox` job runs it on both channels for every pull request, one pinned version each (the job's matrix in `.github/workflows/ci.yml`), so a green CI run already covers the automated rows of both columns at those versions. On macOS 27, running `just e2e_firefox` locally from a terminal inside another app (such as an editor's or a coding app's terminal pane) fails with "Your Firefox profile cannot be loaded", because geckodriver starts Firefox as its own child and macOS refuses that Firefox its own app-data folder (#465); run it from macOS's Terminal app instead, or rely on CI. Setup for every session: `just build_firefox`, then either `just run_firefox` (throwaway profile; on macOS it starts Firefox through `open`, via `scripts/firefox_via_open.sh`, to avoid that same block (#465); `bunx web-ext run --source-dir builds/firefox --firefox /path/to/firefox` picks the channel) or `about:debugging#/runtime/this-firefox` → "Load Temporary Add-on" → any file inside `builds/firefox/`. Use a test site that sets cookies + localStorage (e.g. an httpbin cookie page plus any site with a consent banner), and keep the extension's Debug Mode on so the background console narrates decisions.

Channels: **ESR** = the oldest Firefox ESR that Mozilla still updates and the manifest still supports (`FIREFOX_STRICT_MIN_VERSION` in `scripts/firefox_manifest.ts`), which is ESR 140 as of September 2026. `FIREFOX_ESR` in Mozilla's product details (https://product-details.mozilla.org/1.0/firefox_versions.json) names the current one. **Rel** = the current Firefox release. Both labels stay generic because both channels move; each run records the exact versions under Runs.

## Recording results

Put `OK`, `FAIL #NNN` (issue number), or `SKIP (reason)` in each channel cell, plus the run date and Firefox versions at the top of this section when a full pass completes.

### Runs

One line per full pass, newest first: `YYYY-MM-DD, vX.Y.Z (or commit): ESR <exact version>, Rel <exact version>; N OK, N SKIP, N FAIL`.
